# 设计取舍

记录几个关键决定：为什么这样做、放弃了什么、验证结果如何。

---

## 1. 不用向量检索

### 背景

同类项目普遍用「embedding + 向量库」，理由是能跨表述匹配（「投标保证金」↔「投标担保」）。

### 我们的做法

纯中文 bigram BM25 + 结构感知扩展：

1. **标题命中即扩展**：命中「3 投标人资格要求」这种短标题时，自动带出同页后续正文
2. **表格表头命中即扩展**：带出整表，避免只看到表头看不到数据行
3. **跨页表合并**：表头签名相同的多个证据块视为同一张表（评分表常被切在 4 个页面上）
4. **评分问题强制召回**：按「分值 / 评审因素 / 满分」特征二次检索

### 为什么不选另一种

| 考虑 | 向量检索 | BM25 + 结构扩展 |
|---|---|---|
| 跨表述匹配 | ✅ 强 | ❌ 弱（靠关键词） |
| 表格行定位 | ❌ 切块后丢失行结构 | ✅ 天然按行 |
| 页码准确性 | ❌ 难以回溯页码 | ✅ 8 字短语反查 |
| 部署成本 | ❌ 需 embedding 模型 / GPU | ✅ 纯 CPU、零依赖 |
| 可解释性 | ❌ 相似度黑盒 | ✅ 能说清为什么命中 |
| 调试成本 | ❌ 要重建索引 | ✅ 改代码即生效 |

招标文件是**强结构文档**，条款有明确编号，用户提问也多用原文词汇（「最高限价」「投标保证金」「资格要求」）。关键词命中率足够高，结构扩展补齐了「只有标题没有内容」的问题。

### 验证结果

28 条人工验证问题（7 份文件 × 4 类问题）：

| 阶段 | 通过 |
|---|---|
| 初始实现 | 18/28 |
| + 标题上下文扩展 | 23/28 |
| + 跨页表合并 | 23/28（分布改善，2 个退化为 2 个新过） |
| + 评分特征召回 | 26/28 |
| + 候选规模控制 + 提示词 | **28/28** |

### 什么时候应该换

- 用户开始用大量同义词提问，且无法通过扩充关键词解决
- 引入非结构化章节（如技术方案无编号描述）
- 需要语义去重（同一含义的多个表述合并）

## 2. 表格按行拆解 + 页码反查

### 问题

固定字符切片会让跨页表格变成一个语义混杂的块。极端例子：

```
采购包 | 最高限价
1      | 487.6482 万元
2      | 15.3 万元
3      | 14.8 万元
4      | 8 万元
```

整块 embedding 是「多个金额的平均」，匹配任何「限价是多少」的问题都不精确，且模型容易把第 3 包的 14.8 万答成第 2 包的 15.3 万。

### 做法

1. HTML parser 还原 `colspan` / `rowspan`，重建每个单元格的真实列位
2. 每行成为独立检索单元，`evidence_id` 加 `-R<行号>` 后缀
3. **页码反查**：每行取前 48 字切片成 8 字短语，在 PDF 文本层查这些短语出现的页
4. 如果某页命中 ≥2 个短语且唯一最高分 → 判定该行在第 N 页，`page_verified=true`
5. 否则保留 MinerU 给的页码，标记 `page_verified=false`，前端显示「表格行页码待核对」

### 代价

- 索引规模膨胀（一张 40 行表产生 40 个单元）
- 反查增加导入后首次查询耗时（用 `lru_cache` + 文件指纹缓存）
- 部分表格行仍无法定位（PDF 文本层顺序与视觉顺序不一致时）

### 收益

「4 个标包保证金分别是 50000 / 2500 / 2500 / 1500」这类问题，答案与页码完全对应，切换标包不串行。这是同类项目里少见的确定性保证。

## 3. 三态判定：缺失 ≠ 不满足

### 问题

「公司能不能投这个标」最容易犯的错是把「没查到」当成「不满足」。

### 定义

| 状态 | 判定条件 |
|---|---|
| `met` | 公司证据明确支持 |
| `unmet` | 公司证据明确违反（如证照过期） |
| `unknown` | 证据缺失、含糊、不可比 |

**关键约束**：公司档案里没登记某个证照 → `unknown`，不是 `unmet`。

理由：档案是用户手工维护的，漏填很常见。判成 `unmet` 会让用户误以为「我不符合」，而实际可能是「我忘了填」。

### 适用范围分离

`unmet` 只在两种情况出现：

1. 证照明确过期（有日期可比）
2. 未来的量化指标（如业绩金额不足）

`unknown` 覆盖：

1. 档案未登记该证照
2. 原文适用范围本身是 `pending`
3. 需要报价决策的项目（保证金金额、最高限价）—— 这类明确告知「取决于投标报价决策，不属于公司资质」

### 代价

用户会看到大量「待确认」，需要人工逐条判断。这是刻意的：宁可让人确认，也不能给错误的「不满足」结论。

## 4. 规则优先，模型只做改写

### 分工

| 任务 | 谁做 | 原因 |
|---|---|---|
| 保证金金额 | 正则 | 格式固定，模型易错 |
| 最高限价 | 正则 | 同上 |
| 标包号识别 | 正则 + 汉字数字转换 | `第一包` / `标段一` / `1包` 变体多 |
| 免收判定 | 正则 + 语境 | `不收取` / `无需提交` / `☑不需要` |
| 许可证适用范围 | 正则 | `标段一至四须具有` |
| 评标方法 | 符号 + 关键词 | `☑综合评分法` |
| 废标条款改写 | **模型** | 需要理解语义并组织成「条件 + 动作」 |
| 问答 | **模型** | 同上 |

### 为什么不全部交给模型

实测发现模型读取分段写的限价会漏读（`最高限价：\n1标段：75万`），而正则补一条规则就稳定了。而且规则有回归测试保护，模型输出没有。

### 代价

规则是长尾的。许可证只识别「标段 X 须具有《…许可证》」，遇到「应当具备出版物经营许可资质」这种变体就漏。因此必须维护回归测试，每次补规则后跑一遍防止改坏其他文件。

## 5. Agent 引用硬校验

### 问题

RAG 最大的风险是模型编造引用。让模型「请只引用给定编号」并不可靠。

### 做法

```python
# 工具每次返回证据时登记到 seen
self.seen[ref] = unit

# 作答时校验
valid = [ref for ref in ids if ref in self.seen]
if not valid:
    # 拒绝本轮，把有效编号回喂要求重答
    messages.append({"error": "evidence_ids 必须来自工具结果", "known_ids": list(self.seen)[:40]})
```

三层保障：

1. **白名单**：只能引用工具实际返回过的编号
2. **重答机制**：引用无效时不直接失败，而是告知有效编号让它重写
3. **兜底展示**：多次重答仍失败时，把 agent 实际查到的证据交给人工核对，并明确说「没有找到依据」

### 代价

增加一轮模型调用（约 2-5 秒）。但相比给用户一个带假引用的答案，这个代价是必要的。

## 6. 不用 LangChain / LangGraph

### 做法

`tender_agent.py` 手写 314 行，包含工具定义、循环控制、引用校验。

### 为什么不选框架

| 需求 | 框架 | 手写 |
|---|---|---|
| 5 个工具 | 需要适配层 | 字典 + lambda |
| 引用硬校验 | 需自定义 callback | 10 行代码 |
| 调试 | 多层封装难定位 | 直接 pdb |
| 依赖 | LangChain + 若干 transitive | 0 |
| 升级风险 | 框架 API 变动 | 无 |

Agent 的核心逻辑就是「循环 → 模型决策 → 执行工具 → 回喂结果」，50 行能写完。引入框架反而增加理解成本和维护负担。

### 什么时候应该换

- 工具数超过 20 个，需要自动路由
- 需要复杂的状态机（多 agent 协作、条件分支）
- 需要框架提供的可观测性面板

## 7. 文件存储 + SQLite，不上 Postgres

### 划分

| 数据 | 存储 | 原因 |
|---|---|---|
| PDF 原件 | 文件 | 二进制大文件 |
| `evidence.json` | 文件 | 单份可达数万条，不适合 DB 行 |
| `risk_report.json` | 文件 | 同上，且是整体读写 |
| 用户 / 会话 / 群组 / 授权 / 确认记录 | **SQLite** | 需要事务、并发、按条件查询 |

### 为什么不全用 SQLite

`evidence.json` 单份可达 2MB+ JSON，读一次要整体反序列化。放进 SQLite 反而更慢，且失去「直接看文件调试」的便利。

### 为什么确认记录必须进 DB

`review_state.json` 是整体读写，多人同时确认会丢更新。SQLite 的 `INSERT OR REPLACE` + 事务能保证原子性，已用 `test_team_sharing.py` 的并发测试验证。

### 什么时候应该换 Postgres

- 多实例部署（SQLite 不支持跨进程写）
- 需要按项目名、日期、金额做复杂查询
- 团队规模超过 10 人并发

## 8. 前端不引入框架

### 做法

原生 JS 1,388 行 + 设计系统 CSS 1,563 行，无构建步骤。

### 理由

- 页面结构稳定（4 个视图），不需要路由
- 状态简单（当前文档、当前标包、确认集合）
- 零构建意味着改完刷新即见，调试成本最低
- 部署只需静态文件服务

### 代价

- 代码组织靠约定（按功能分段 + 注释）
- 复用靠函数封装（`node()` / `sourceButtons()`）
- 规模继续增长会难以维护

### 什么时候应该换

- 视图增加到 10 个以上
- 需要多人并行开发前端
- 需要组件级状态共享

## 9. 回归测试的边界

### 现在的覆盖

| 层 | 测试 |
|---|---|
| 抽取正确性 | `test_packages.py` 25 例：金额、页码、三态分布、全量快照 |
| 问答正确性 | `test_qa.py` 56 例：28 问题 × 答案事实 / 引用合法性 |
| 比对逻辑 | `test_document_compare.py` |
| 并发与权限 | `test_team_sharing.py` |
| 端到端导入 | `e2e_import.py` |

### 未覆盖的

- **检索召回率**（Recall@K）：没有标注集，只有间接指标（问答通过率）
- **模型输出稳定性**：同一问题多次调用结果可能不同，测试只校验关键事实
- **OCR 质量**：扫描件解析效果取决于 MinerU，无法本地回归
- **大规模性能**：未测 200 份文档时的响应时间

### 一个设计选择

`test_qa.py` 校验的是「答案是否包含关键事实」+「引用是否合法」，而不是「答案是否逐字匹配」。因为模型有非确定性，逐字比对会产生大量假失败。这个取舍牺牲了严格性，换来测试可用性。
